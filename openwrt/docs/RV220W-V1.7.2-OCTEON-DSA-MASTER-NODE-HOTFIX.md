# RV220W v1.7.2 Octeon DSA master-node hotfix

## Evidence

The v1.7.1 image loaded `tag_brcm`, but B53 still returned probe deferral and
created no DSA user ports. `eth0` existed, while the DSA CPU port referenced the
per-port `ethernet@0` device-tree node.

The staging Octeon driver obtains that per-port node in `priv->of_node`, but
calls `SET_NETDEV_DEV(dev, &pdev->dev)`, associating all three netdevs with the
common PIP platform node. DSA uses `of_find_net_device_by_node()` to resolve the
CPU-port `ethernet` phandle. Because the netdev itself did not expose
`priv->of_node`, the lookup returned NULL and DSA returned `-EPROBE_DEFER`.

## Change

The DSA build temporarily injects a kernel patch that assigns:

```c
dev->dev.of_node = priv->of_node;
```

before `register_netdev()`. The patch also logs the numeric B53/DSA registration
error if registration still fails.

The build helper restores the exact original DTS and target patch-directory
state after staging the RAM-only image.

## Network cleanup

The DSA first-boot configuration now removes:

- the anonymous generic `br-lan` device that still referenced `eth0`;
- `wan6`, which otherwise raised excluded `eth1`;
- any previous named DSA bridge and LAN interface before rebuilding them.

It then creates a single `br-lan` containing `lan1` through `lan4` at
`192.168.240.2/24`.

## Safety

The platform baseline remains v1.3.2. The patch is used only while building the
RAM/TFTP DSA candidate, is removed from the OpenWrt source tree afterward, and
does not add any flash-writing path.
