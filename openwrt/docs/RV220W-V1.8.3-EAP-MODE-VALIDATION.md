# RV220W v1.8.3 standalone EAP-mode validation

## Run 7 result

The failed `wan@eth1` and working `wan@eth0` B53 snapshots rule out the v1.8.0 PVLAN callback as the remaining fault.

Failed `wan@eth1`:

- port 0 PVLAN: `0x0021` (`{0,5}`)
- port 5 PVLAN: `0x0021` (`{0,5}`)
- port 8 PVLAN: `0x011e` (`{1,2,3,4,8}`)
- Broadcom header control: `0x03` (ports 5 and 8 enabled)
- global management configuration: `0xc2`; bits 7:6 are `0b11`, the dual-IMP selection
- `eth1` RX remains zero

Working `wan@eth0`:

- port 0 PVLAN becomes `0x0101` (`{0,8}`)
- port 8 PVLAN becomes `0x011f` (`{0,1,2,3,4,8}`)
- port 5 retains `0x0021`
- no other captured control/header register changes

The affinity callback therefore programs the expected hardware membership in both states. The next unmeasured state is the 64-bit EAP configuration for port 0.

## Why EAP is now the leading test

Linux 6.12 stable sets B53 standalone user ports to `EAP_MODE_SIMPLIFIED`. That mode redirects frames with unknown source addresses to a CPU/management port. Bridge join changes the port to `EAP_MODE_BASIC`; bridge leave restores simplified mode.

The WAN port is standalone, while LAN1-LAN4 are bridge members. The user also recalls that forwarding began only after a manual simplified-to-basic change. This is consistent with reports that the simplified-mode B53 change broke standalone WAN ports on some Broadcom switches.

The test must still be measured on this BCM53115. v1.8.3 does not install a permanent kernel workaround.

## Tooling

The passive B53 report now includes for every port:

- `eap_config_raw`
- `eap_mode_code`
- `eap_mode`

It also decodes global management bits 7:6 as `frame_management_mode`; the expected current result is `dual-imp-port8-port5`.

`b53-eap` uploads a narrowly restricted target helper over UART. Write actions:

- preserve all EAP configuration bits except mode bits 52:51;
- permit only external user ports 0 through 4;
- save the first observed original value in `/tmp/rv220w-b53-eap-portN.original`;
- verify readback;
- restore pseudo-PHY selectors;
- never write flash.

## Controlled test

Start with `wan@eth1`, cable in WAN, and host `192.168.241.1/24`.

```fish
./rv220w.fish collect-conduit run8-eth1-pre-eap --force-upload
./rv220w.fish b53-eap show --eap-port 0 --force-upload
```

Set BASIC without changing the conduit or cycling the link:

```fish
./rv220w.fish b53-eap set-basic --eap-port 0 --force-upload
sudo ip neigh flush dev enp0s31f6
ping -I enp0s31f6 -c 20 192.168.241.2
ping -I enp0s31f6 -M do -s 1472 -c 20 192.168.241.2
./rv220w.fish collect-conduit run8-eth1-basic-after --force-upload
```

If BASIC works, reproduce the failure with SIMPLIFIED:

```fish
./rv220w.fish b53-eap set-simplified --eap-port 0
sudo ip neigh flush dev enp0s31f6
ping -I enp0s31f6 -c 10 192.168.241.2
./rv220w.fish collect-conduit run8-eth1-simplified-after --force-upload
```

Restore the first saved state:

```fish
./rv220w.fish b53-eap restore --eap-port 0
```

A reboot also discards every live change because this remains a RAM-only test.

## Interpretation

- BASIC works and SIMPLIFIED fails: implement a generic B53 multi-CPU standalone policy that relies on per-port PVLAN affinity rather than the global simplified redirect.
- Both fail: EAP is not the remaining port-5 blocker; retain the measured register evidence and investigate CPU-port-5 ingress classification/IMP handling next.
- Both work: the earlier manual transition changed an additional state not yet captured; compare all run8 reports before modifying the driver.
