# RV220W toolkit v1.9.0: hardware-proven full-RJ45 profile
> **Hardware status, 2026-07-27:** the v1.9.0 `rj45-full` image has now been fully booted by TFTP from RAM and has initialized and operated all five RJ45 ports. The stable filename is retained because tests and historical references use it. LuCI, Wi-Fi, and persistent flash remain outside this result.

## Scope

v1.9.0 is the first RAM-only profile proven to operate as a conventional
five-port OpenWrt wired router:

```text
WAN jack   -> BCM53115 port 0 -> CPU port 5 -> eth1 -> wan
LAN1-LAN4  -> BCM53115 ports 1-4 -> CPU port 8 -> eth0 -> br-lan
```

It retains all previously proven Octeon and DSA corrections and adds the run9
VLAN fix as kernel patch 998.

## Kernel patches

1. `995-rv220w-octeon-dsa-master-node.patch`
2. `996-octeon-dsa-conduit-length-error.patch`
3. `997-b53-multi-conduit-affinity.patch`
4. `998-b53-enable-dt-cpu-ports.patch`

Patch 998 is generic B53 behavior.  It merges DSA CPU ports from firmware into
`dev->enabled_ports` before switch reset/configuration.  On BCM53115 this makes
port 5 participate in the generic default VID-0 initialization instead of
retaining stale bootloader VLAN state.

## OpenWrt policy

The `rj45-full` profile enables:

- LAN bridge containing only `lan1` through `lan4`;
- LAN address `192.168.240.2/24` to preserve the proven TFTP lab subnet;
- dnsmasq DHCPv4 and odhcpd IPv6 service on LAN;
- DHCP and DHCPv6 clients on `wan`;
- firewall4 with separate LAN and WAN zones;
- LAN-to-WAN forwarding, masquerading, and MTU fixing;
- PPP and PPPoE packages for later software configuration;
- no LuCI and no flash-write automation.

The internal default VID is not a user WAN VLAN.  Tagged provider service is
configured normally above the DSA interface, for example `wan.35`.

The packaged firewall overlay preserves OpenWrt's stock allow rules. Consequently,
WAN-to-router ICMP may be allowed even though unsolicited WAN-to-LAN forwarding
is rejected. Test isolation with a separate LAN host and forwarding attempt, not
only by pinging the router's own WAN address.

## Build

```fish
./rv220w.fish doctor
./rv220w.fish platform verify
./rv220w.fish build rj45-full
```

Expected artifact:

```text
~/src/rv220w-openwrt/artifacts/rv220w-openwrt-rv220w-rj45-initramfs.elf
```

## RAM boot

```fish
./rv220w.fish tftp-boot \
    --profile rj45-full \
    --interface enp0s31f6 \
    --configure-interface
```

The boot helper uses the already proven `192.168.240.1` host and
`192.168.240.2` target addresses.  After boot, LAN remains at
`192.168.240.2`; WAN begins DHCP independently.

## Regression acceptance sequence

At the router console:

```sh
rv220w-rj45-status
ip -d link show dev wan
ip -d link show dev lan1
ubus call network.interface.wan status
nft list ruleset
```

On a host connected to each LAN jack:

```sh
ping -c 20 192.168.240.2
ping -M do -s 1472 -c 20 192.168.240.2
```

Then connect WAN to an upstream DHCP network and verify:

```sh
ubus call network.interface.wan status
ping -I br-lan -c 4 1.1.1.1
```

Also verify isolation with two hosts:

- a host on WAN must not ARP directly for a LAN host;
- unsolicited WAN-to-LAN forwarding must fail;
- LAN-to-WAN traffic must pass through Linux/firewall4, not switch directly;
- port-0/5 and port-1-4/8 MIB counters must follow their intended conduits.

## Status boundary

The source, patch application, package policy, generated build workflow, complete
TFTP RAM boot, and operation of all five RJ45 ports are hardware-proven. The
result remains experimental: LuCI and Wi-Fi are absent, no persistent image is
claimed, and no onboard NOR erase or program attempt has been made.
