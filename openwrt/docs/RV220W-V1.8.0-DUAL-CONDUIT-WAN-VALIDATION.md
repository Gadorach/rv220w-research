# RV220W v1.8.0 dual-conduit WAN validation

## Purpose

This stage preserves the proven LAN path and adds the second BCM53115 CPU conduit:

```text
WAN / BCM53115 port 0 ─ BCM53115 CPU port 5 ─ Octeon eth1

LAN1-LAN4 / ports 1-4 ─ BCM53115 CPU port 8 ─ Octeon eth0
```

The image remains TFTP/RAM-only. DSA may reset and reconfigure volatile switch state, but no workflow writes NOR or invokes a flash utility.

## Why an affinity helper is required

With two CPU ports in one DSA tree, Linux initially associates user ports with the first eligible CPU port. Port 5 precedes port 8 numerically, so the generated DSA interfaces can initially appear on `eth1`. Before netifd raises the network, `/usr/sbin/rv220w-dsa-affinity` uses the standard DSA rtnetlink operation to enforce:

```text
wan       -> eth1
lan1-lan4 -> eth0
```

The helper performs no raw MDIO or switch-register writes. An early init script applies the mapping before the network service, and an idempotent net hotplug hook covers unusual module ordering.

## Generic B53 multi-conduit support

Linux DSA exposes conduit reassignment through `ip link set DEV type dsa master CONDUIT`, but only when the switch driver implements `port_change_conduit`. Upstream B53 does not currently provide that callback, and its legacy IMP VLAN setup assumes one CPU port. Toolkit v1.8.0 therefore installs `997-b53-multi-conduit-affinity.patch` through OpenWrt's normal Octeon target patch set.

The patch is switch-generic. For multi-CPU B53 trees it:

- preserves each user port's existing bridge/user membership;
- removes all old CPU-port bits and adds only the DSA-assigned CPU port;
- rebuilds each CPU port's membership from the users currently assigned to it;
- updates B53's cached user-port VLAN-control mask;
- retains the existing single-CPU implementation unchanged.

The userspace affinity helper requests `wan -> eth1` and `lan1-lan4 -> eth0` through the standard DSA rtnetlink API before netifd raises the interfaces.

## Network policy

The validation image deliberately avoids router policy while the second physical path is being proven:

| Interface | Address | Role |
|---|---|---|
| `br-lan` | `192.168.240.2/24` | LAN1-LAN4 bridge |
| `wan` | `192.168.241.2/24` | Isolated WAN test endpoint |

There is no DHCP server/client, default gateway, DNS, NAT, forwarding or firewall configuration in this profile. The two subnets terminate locally and cannot route through the RV220W.

## Build profiles

First candidate:

```fish
./rv220w.fish build dsa-dual
```

This uses `rgmii-rxid` for both CPU ports and produces:

```text
$RV220W_WORKSPACE/artifacts/rv220w-openwrt-rv220w-dsa-dual-rxid.elf
```

Alternative WAN-only timing experiments are included but must not be tested unless the first candidate fails to pass traffic while the port-5 link remains up:

```text
rv220w-dsa-dual-wan-txid
rv220w-dsa-dual-wan-rgmii
```

Port 8 remains fixed at the proven `rgmii-rxid` setting in every dual profile.

## First boot and LAN regression gate

Boot through LAN1 exactly as before:

```fish
./rv220w.fish tftp-boot \
    --profile dsa-dual \
    --interface enp0s31f6 \
    --configure-interface
```

Collect initial state:

```fish
./rv220w.fish collect-dsa run6-dual-LAN-before
```

Expected evidence:

```text
DSA: tree 0 setup
wan@eth1
lan1@eth0 through lan4@eth0
affinity_check=ok
br-lan = 192.168.240.2/24
wan = 192.168.241.2/24
```

Verify that the existing LAN path still responds:

```fish
sudo ip addr replace 192.168.240.1/24 dev enp0s31f6
sudo ip neigh flush dev enp0s31f6
ping -I enp0s31f6 -M do -s 1472 -c 20 192.168.240.2
```

## WAN test with one host interface

After the LAN regression test, move the same cable from LAN1 to the WAN jack and wait for link. Change only the host-side address:

```fish
sudo ip addr replace 192.168.241.1/24 dev enp0s31f6
sudo ip neigh flush dev enp0s31f6

ip -s link show dev enp0s31f6
ping -I enp0s31f6 -c 20 192.168.241.2
ping -I enp0s31f6 -M do -s 1472 -c 20 192.168.241.2
ip neigh show dev enp0s31f6
ip -s link show dev enp0s31f6
```

Collect the WAN state over UART:

```fish
./rv220w.fish collect-dsa run6-dual-WAN-after
```

The WAN gate passes when:

- `wan@eth1` reports carrier and 1000/full;
- `wan` counters increase without errors or drops;
- `eth1` conduit counters track the WAN traffic;
- ARP resolves `192.168.241.2`;
- normal and 1500-byte IPv4 pings return without loss;
- LAN interfaces remain assigned to `eth0` and outside the WAN L2 domain.

Restore the host test address before another LAN boot/test:

```fish
sudo ip addr replace 192.168.240.1/24 dev enp0s31f6
```
