# RV220W v1.7.6 — Octeon DSA receive-length compatibility

## Evidence

The v1.7.5 `rgmii-rxid` image completed B53/DSA registration, created
`lan1` through `lan4`, formed `br-lan`, and moved LAN1 to forwarding.
Ingress traffic then produced repeated Octeon PIP receive error code 10
and was discarded before the DSA receive path could decode the Broadcom
tag.

Octeon error code 10 denotes a mismatch between the received frame length
and the value occupying the normal Ethernet length/type location.  The
four-byte Broadcom DSA tag is inserted after the source MAC address and
therefore temporarily occupies that location.  The existing Octeon
short-frame exception accepts code 10 only for frames of 64 bytes or
less; adding the DSA tag moves minimum-size frames beyond that limit.

## Kernel-side correction

The standard Octeon target patch
`996-octeon-dsa-conduit-length-error.patch` retains the existing minimum-
frame exception and also accepts error code 10 when the receiving Octeon
netdev is actively registered as a DSA conduit.  The packet then follows
the normal `eth_type_trans()` and DSA tag receive path, which remains
responsible for validating and decoding the tag.

The patch changes only `drivers/staging/octeon/ethernet-rx.c`.  It has no
B53, board-name, or OpenWrt-core special case and does not relax receive
error handling on non-DSA Octeon ports.

## Validation scope

Rebuild and RAM-boot the `dsa-lan`/`rgmii-rxid` candidate.  Collect DSA
snapshots before and after ARP/ping traffic.  Success requires the error-
10 stream to stop, LAN1 RX counters to advance, ARP resolution to
complete, and `192.168.240.2` to answer through `br-lan`.  Do not move to
the alternate RGMII timing variants unless the tagged data path remains
unreliable after this receive-path correction.
