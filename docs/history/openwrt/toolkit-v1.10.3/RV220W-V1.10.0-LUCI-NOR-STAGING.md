# RV220W v1.10.0: LuCI and guarded parallel-NOR staging

## Status entering this stage

Toolkit v1.9.3 is the validated all-RJ45 RAM baseline. The retained evidence
proves LAN1-LAN4, WAN DHCP, LAN DHCP, routing/NAT, firewall4 WAN-to-LAN
isolation, clean raw-FDT export, readable NOR partitions, and an untainted
production kernel.

The secondary Octeon `eth1` master and BCM53115 port-5 Tx counters may remain
zero even while the DSA `wan` netdev and real WAN traffic work. Acceptance uses
the DSA user-port counters and end-to-end DHCP/routing results.

## Storage terminology

The RV220W has a **32 MiB x16 parallel CFI NOR**, not NAND. v1.10.0 uses NOR
terminology throughout and does not introduce NAND tools or assumptions.

## Build profiles

### `rj45-full`

The validated full-RJ45 profile remains available and keeps all seven MTD
regions read-only. Kernel patches 995-999 and the production DTS are unchanged.

### `rj45-luci`

This profile adds `luci-light` and uHTTPd above the validated RJ45 profile.
LuCI is bound only to:

```text
http://192.168.240.2/
```

No HTTPS listener is enabled in this first size-constrained stage. The normal
seven-partition all-read-only command line remains in use.

The build emits:

```text
rv220w-openwrt-rv220w-rj45-luci-initramfs.elf
rv220w-openwrt-rv220w-rj45-luci-nor-slot.bin
rv220w-openwrt-rv220w-rj45-luci-nor-slot.json
rv220w-openwrt-rv220w-rj45-luci-nor-slot.bin.sha256
```

The slot image is exactly 22 MiB. It begins with the LuCI initramfs ELF and is
padded with `0xff`. The build fails if the ELF exceeds the slot.

### `nor-writer`

This image must be booted through TFTP/RAM. It uses the same production DTS and
RJ45 stack, but intentionally excludes LuCI and raw MDIO diagnostics. It uses a
separate OpenWrt device target whose command line exposes:

```text
512 KiB  boot-chain      read-only
22 MiB   openwrt-slot    writable
1 MiB    stock-data      read-only
128 KiB  legacy-env-gap  read-only
8448 KiB vendor-tail     read-only
128 KiB  uboot-env       read-only
```

Only `openwrt-slot` can receive a Linux MTD write. The writer helper refuses to
operate unless the board identity, profile marker, MTD name, exact size and
128 KiB erase geometry all match.

## First-stage persistence model

The first payload is still an initramfs image. Storing it in NOR makes the
firmware image persistent, but the running root filesystem and configuration
remain volatile. Every boot starts from the baked-in defaults.

Persistent SquashFS plus overlay, automatic boot selection, and any U-Boot
environment change are separate later stages.

## Guarded write flow

1. Build both profiles:

```fish
./rv220w.fish build rj45-luci
./rv220w.fish build nor-writer
```

2. RAM-boot the writer:

```fish
./rv220w.fish tftp-boot --profile nor-writer --interface enp0s31f6 --configure-interface
```

3. Set a temporary root password through UART:

```sh
passwd
```

4. Verify the writer target and create a full 22 MiB backup:

```fish
./rv220w.fish nor-stage status
./rv220w.fish nor-stage backup
```

5. Write only after reviewing the generated slot manifest:

```fish
./rv220w.fish nor-stage write --confirm RV220W_WRITE_OPENWRT_SLOT
```

The host workflow automatically creates another complete slot backup before
transfer or erase. v1.10.2 streams the binary through SSH rather than modern
`scp`/SFTP, because the minimal Dropbear writer intentionally has no SFTP
server. Expected initramfs host keys are kept out of persistent `known_hosts`. The target validates the image SHA-256, writes only
`openwrt-slot`, reads back the entire 22 MiB region, and compares SHA-256.
It does not reboot.

6. At the serial U-Boot prompt, test the staged image manually:

The original v1.10.0 instructions proposed direct `bootoct` execution from
`0xbdc80000`. Hardware testing in run15 proved that command invalid for the
Linux ELF. Use the v1.10.3 manifest-derived NOR-to-RAM sequence instead:

```text
cp.b 0xbdc80000 0x05500000 0x11565d0
bootoctlinux 0x05500000 console=ttyS0,115200
```

No `saveenv`, boot command change, bootloader write, environment write, or
automatic reboot is included.

## Recovery

The existing TFTP RAM boot remains the recovery path. The preserved 22 MiB backup contains the original stock kernel/rootfs region.
After RAM-booting the same writer image, restore it only to the same slot with:

```fish
./rv220w.fish nor-stage restore \
    --image ~/src/rv220w-openwrt/backups/nor/rv220w-openwrt-slot-backup-<timestamp>.bin \
    --confirm RV220W_RESTORE_OPENWRT_SLOT
```

The restore path makes a fresh backup of the current slot first, validates the
exact 22 MiB size and SHA-256, writes only `openwrt-slot`, and performs a full
read-back hash. It still cannot touch the boot chain, environment, stock-data,
legacy gap, or vendor tail.

## Tooling corrections

- `collect-conduit` now treats absent production MDIO diagnostics as a clean
  skip unless `--require-b53` is used.
- B53 availability is checked before the slow UART scanner upload.
- Failed B53 target reports are retrieved when available.
- `collect-rj45` captures the production acceptance state without raw MDIO.
- stale `*-build-serial.log` files are deleted before a new build and are
  recreated only by a current serial fallback.
