# RV220W v1.13.1 exact sysupgrade root hotfix

> **Superseded by v1.13.2:** this hotfix removed Octeon's inherited 128 KiB
> padding recipe, but the standard `sysupgrade-tar.sh` still aligns the root
> member to 1024 bytes. See `RV220W-V1.13.2-STANDARD-SYSUPGRADE-PADDING.md`.

The v1.13.0 build completed the kernel and SquashFS components but rejected the
sysupgrade tar because its `root` member was 131,332 bytes larger than the raw
SquashFS. The member began with the exact SquashFS bytes and the remainder was
all zero.

Octeon `Device/Default` defines a filesystem-specific
`IMAGE/sysupgrade.tar/squashfs` recipe using `append-rootfs | pad-extra 128k`.
That inherited recipe takes precedence over a generic per-device
`IMAGE/sysupgrade.tar` assignment.

The persistent RV220W target now explicitly overrides the filesystem-specific
recipe:

```make
IMAGE/sysupgrade.tar/squashfs := sysupgrade-tar | append-metadata
```

The verifier remains strict: the tar `kernel` and `root` members must match the
staged gzip kernel and raw SquashFS byte-for-byte. This avoids carrying zero
padding into the beginning of the automatically split JFFS2 overlay.

No runtime MTD writer, flash layout, boot chain, U-Boot environment, kernel,
rootfs contents, or persistent-writer behavior changed in this hotfix.
