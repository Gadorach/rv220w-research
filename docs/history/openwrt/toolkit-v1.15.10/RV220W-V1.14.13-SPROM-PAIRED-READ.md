# RV220W v1.14.13 — stock-compatible paired 16-bit SPROM capture

## Hardware result carried forward from v1.14.12

The v1.14.12 RAM image built and booted successfully with the non-binding `kmod-ssb-nvmem-diag` module. Passive ChipCommon evidence from the BCM4322 reported:

```text
chip=0x4322
ccrev=23
chipstatus=0x00068040
bcm4322_sprom_otp_sel=1
bcm4322_stock_source=sprom
ready=1
status_fresh=0
```

For BCM4322, selector `1` means stock firmware selects the external SPROM. The optional OTP `init-shadow` path therefore remains ineligible and is **not** part of this test.

The existing Linux physical-SPROM capture is still a 220-word/rev8-shaped image with an invalid CRC. Its notable structural anomaly is that nearly all meaningful non-`0xffff` values occur on one word parity, while the opposite parity is predominantly erased. That is evidence of a read-path anomaly worth testing, but it is not itself permission to reconstruct or interleave calibration data.

## Stock `wl.ko` low-level access result

Offline disassembly of the preserved Broadcom 5.60.120.9 `wl.ko` identifies the helper called by `srom_read`. Its loop:

1. advances SPROM addresses by two bytes per word;
2. performs a 16-bit load at the current SPROM address;
3. byte-swaps and stores that first result;
4. performs a **second 16-bit load at the same address** immediately afterward;
5. byte-swaps and stores the second result over the first;
6. then advances to the next word.

Thus the stock driver's effective SPROM image is the complete stream produced by the **second transaction at each word address**. It does not use a four-byte stride and this finding does not justify 32-bit SPROM accesses.

The preserved stock kernel's exported `ioread16()` also resolves to a halfword load plus byte-swap on Octeon, consistent with the stock `wl.ko` helper using a 16-bit MMIO access model rather than a wider read.

## v1.14.13 diagnostic

The existing non-binding `ssb_nvmem_diag` module now adds:

```text
/sys/bus/pci/devices/<BDF>/ssb_sprom_paired16
```

Reading this attribute:

- chooses the SPROM offset using the same high-level rules as Linux SSB;
- maps only the 440-byte rev4+ SPROM window;
- performs exactly two consecutive `ioread16()` operations for each of 220 addresses;
- preserves both results as independent complete streams;
- reports the number of words where the first and second transaction differ.

Example format:

```text
offset=0x1000 words=220 mismatch_words=N
first=<220 numeric-u16 hex words>
second=<220 numeric-u16 hex words>
```

No 32-bit SPROM read is implemented. The paired-read callback contains no NVM write or PCI configuration write.

## Host-side integrity policy

`analyze-ssb-sprom-paired.py` validates `first` and `second` separately. For each complete 220-word stream it reports:

- SROM revision;
- first-word/erasure sanity;
- canonical SHA-256;
- Linux stored CRC versus calculated CRC;
- Broadcom full-image CRC residue (`0x9f` expected);
- count and parity of nontrivial words.

The existing Linux `ssb_sprom` single-read capture is normalized back to numeric words and compared directly against both paired streams.

The analyzer **never** interleaves first/second transactions, fills erased lanes, copies words between streams, injects the RV220W MAC, or invents RF calibration values. A synthetic regression explicitly constructs a case where parity interleaving would yield a valid image and verifies that emission remains blocked.

Only the complete direct `second` stream may be serialized into OpenWrt fallback-SPROM byte order, and only when it independently satisfies:

1. 220 captured words;
2. non-erased first word;
3. supported SROM revision 4, 5 or 8;
4. Linux stored CRC passes;
5. Broadcom full-image CRC residue is `0x9f`.

CRC success establishes image integrity only. RF remains blocked until the resulting boardflags, PA/TSSI/power tables, chain/antenna/FEM values and regulatory identity are checked against this hardware.

## Next hardware gate

Build and RAM-boot v1.14.13, then run:

```fish
./rv220w.fish collect-wifi sprom-paired-read
```

The decisive cases are:

- **Second stream is complete and CRC-valid:** strong evidence that stock Broadcom's dummy/paired read sequence is required on this PCI/Octeon combination. Proceed to field-by-field calibration audit before RF.
- **First and second are identical to the current invalid shadow:** the double-read hypothesis is rejected; investigate SPROM electrical/content history and any stock initialization preceding `srom_read`.
- **First and second differ but neither is independently valid:** retain both as evidence. Do not interleave them; continue reconstructing the stock pre-read setup and bus sequencing.

Do not run OTP INIT on this board and do not perform DMA/PIO reload, scan, association or AP testing yet.
