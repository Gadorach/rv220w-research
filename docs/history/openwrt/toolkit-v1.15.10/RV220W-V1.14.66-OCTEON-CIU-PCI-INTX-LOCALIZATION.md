# RV220W v1.14.66 — Octeon CIU PCI INTx physical-line localization

## Evidence entering this release

The v1.14.65 hardware run assigns the BCM4322 endpoint (`0000:00:03.0`) Linux IRQ 110 and `/proc/interrupts` identifies it as `CIU 37`, but its count stays zero over the receive window. At the same time b43 reports an enabled generic DMA interrupt plus DMA0 RX_DONE pending. SSB PCI config offsets 0x90/0x94 are both `0x00000200`, consistent with routing SSB core index 1 into the Broadcom PCI core. This moves the unresolved boundary outside b43/PIO and past internal SSB-to-PCI routing.

Current upstream Octeon PCI code has no RV220W-specific mapping and falls back to PCI swizzling. For bus-0 slot 3 with INTA#, that fallback maps to PCI_INT1, which corresponds to CIU bit 37 / IRQ110. That is exactly the assignment observed on hardware; it does not prove the RV220W PCB actually wires the mini-PCI INTA# signal to that Octeon input.

The supplied older Wi5 b43 tree was reviewed as a historical control. Its BCM4322 path also calls `ssb_pcicore_dev_irqvecs_enable()` before requesting the threaded b43 IRQ; it does not contain a separate board-specific interrupt workaround.

## Read-only discriminator

`kmod-octeon-pci-irq-diag` is staged only for the RAM/WLAN profile. On CN50xx it reads:

- `CVMX_CIU_INTX_SUM0(core * 2)`;
- `CVMX_CIU_INTX_EN0(core * 2)`;
- bits 36–39 decoded as PCI INT0–INT3 pending/enabled masks.

Linux's Octeon interrupt controller maps PCI_INT0..3 to those same CIU bits. The module creates only `/sys/kernel/rv220w_octeon_pci_irq_diag/snapshot`. There is no CSR write, IRQ acknowledgement, mask change, IRQ request, PCI config write, or device binding.

The probe additionally reads the first 64 bytes of the BCM4322 PCI config header. The analyzer decodes command/status, Interrupt Line, Interrupt Pin, and the legacy INTx-disable bit.

## Decision tree

With b43 DMA/RX_DONE still pending and host IRQ count still zero:

1. If a CIU PCI bit other than the Linux-assigned bit is pending, the result is a board-level PCI INTx routing mismatch. The following release can then make a narrow RV220W-specific `octeon_get_pci_interrupts()` mapping using the observed physical line.
2. If no CIU PCI bit is pending, the fault remains between the Broadcom PCI core's external INTx assertion and the CN5010 CIU input. Do not change Linux mapping.
3. If the assigned CIU bit is pending and enabled but `/proc/interrupts` stays zero, investigate the CIU/host IRQ delivery path instead of board swizzling.
4. If the endpoint has INTx disabled, investigate why before changing routing.

No route correction is included in v1.14.66.
