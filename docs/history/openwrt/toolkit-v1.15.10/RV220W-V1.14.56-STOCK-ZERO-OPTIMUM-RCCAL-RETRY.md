# RV220W v1.14.56 — stock zero-normalized optimum / RCCAL retry

## v1.14.55 hardware result

The v1.14.55 point-13 request never reached RCCAL. Core0 gain/IQ and core1 PHY/radio remained healthy, but core1 gain returned `-ERANGE` after two iterations.

The decisive telemetry was:

- RX core 1 / opposite TX core 0;
- trace count 2;
- final measured row 4 in `GAIN_UP`;
- row-4 normalized power 16,710, above the 10,000 threshold;
- selected previous-row normalized power 0;
- fail reason `OPTIMUM_RANGE` from the local final diagnostic guard;
- core1 dedicated IQ and RCCAL telemetry remained untouched.

Broadcom rev5 gain control selects the previous row when `GAIN_UP` first crosses the threshold. Its `wlc_phy_nbits(0)` returns 0, so a selected row with normalized power zero is defined: desired-power fine adjustment raises HPVGA and clamps it to the allowed maximum.

## v1.14.56 correction

The gain-control algorithm, table, tones, estimator, threshold and direction state machine are unchanged. The only algorithmic change is removing the local non-stock requirement that the selected optimum's *normalized* power be nonzero.

To retain fail-closed qualification, the diagnostic gates accept a zero-normalized selected optimum only when the measured state proves the expected stock transition:

```text
trace_count >= 2
last_dir == GAIN_UP
last/current normalized power > 10000
```

The measured crossed row must still have real I/Q energy, rotating playback, valid TX gain/high-byte BBMULT, RFSEQCA `0x1221`, BCM2056 routing, no IQEST timeout and no helper failure. Core1 dedicated IQ must then pass before RCCAL is accepted.

For RCCAL's own gain-control invocation, selected optimum power is likewise not required to be nonzero; the subsequent DAC-test reference/target energy, ratio arithmetic, sweep window and six-register commit readback independently prove that the selected gain is usable. An all-zero/no-signal path therefore still cannot qualify.

## Boundary

v1.14.56 exposes the same `rccal-commit` point 13 as v1.14.55. Normal RX-IQ calibration and persistence remain blocked. A successful point-13 capture must still reach the architecture-resolved injected cancellation and restore all transaction state exactly.
