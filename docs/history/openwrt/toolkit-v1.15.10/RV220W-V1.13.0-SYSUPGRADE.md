# RV220W v1.13.0 sysupgrade image

## Qualified prerequisite

The full-NOR rootfs layout is hardware validated. The board exposes a 6 MiB
`openwrt-kernel`, a 25.375 MiB `rootfs`, one automatic 21.375 MiB
`rootfs_data`, and a protected final 128 KiB `uboot-env`. SquashFS, JFFS2 and
configuration persistence survived a complete reboot.

## Build output

Platform v1.7.0 changes the persistent device recipe to:

```make
IMAGES := sysupgrade.tar
IMAGE/sysupgrade.tar := sysupgrade-tar | append-metadata
```

The toolkit stages the result as:

```text
rv220w-openwrt-rv220w-rj45-luci-persistent-sysupgrade.tar
rv220w-openwrt-rv220w-rj45-luci-persistent-sysupgrade.json
```

The JSON report records the archive hash, embedded component hashes and sizes,
metadata identity, limits and write policy. Build staging fails if OpenWrt's
host `fwtool` cannot extract valid metadata supporting `cisco,rv220w`.

## Runtime checks

`platform_check_image` requires:

- appended OpenWrt metadata;
- `CONTROL` containing exactly `BOARD=cisco,rv220w`;
- gzip kernel magic and size no greater than 6 MiB;
- SquashFS root magic and size no greater than 25.375 MiB;
- the exact validated physical MTD sizes;
- exactly one automatic `rootfs_data` at `mtd3` with the 128 KiB erase size.

The automatic child size is not fixed by the upgrade guard. It changes by
whole erase blocks when a future SquashFS becomes larger or smaller; only the
physical `boot-chain`, `openwrt-kernel`, `rootfs`, and `uboot-env` map is fixed.

## Stage2 write order

The upgrade implementation extracts both components into the RAM filesystem,
then performs:

```text
unlock rootfs
erase complete rootfs
write SquashFS, with mtd -j when preserving configuration
verify SquashFS prefix
unlock openwrt-kernel
erase openwrt-kernel
write gzip kernel
verify gzip kernel
sync
```

The complete rootfs erase is mandatory because the automatic JFFS2 overlay
occupies the unused tail of the same physical MTD partition. The kernel is
written last. Neither the boot chain nor U-Boot environment is a write target.

## Validation boundary

The archive generation, metadata extraction, component identity, size/magic
checks and exact simulated MTD operation sequence are tested by the toolkit.
No real sysupgrade has yet been executed on hardware. The first hardware run
must retain UART, TFTP, the persistent writer and full NOR backups.

The v1.12.0 runtime cannot perform the first sysupgrade because its SquashFS
predates the RV220W platform upgrade implementation. Bootstrap v1.13.0 by the
guarded component path, prove NOR kernel boot, and use `sysupgrade -T` before
allowing a write-producing sysupgrade.
