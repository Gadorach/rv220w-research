# RV220W v1.14.34 — stock RX-IQ cleanup and CalcRxIqComp forensics

## Hardware evidence carried from v1.14.33

The channel-8 active reconstruction completed its primary calibration body (`primary_rc=0`) under verified b43 MAC suspend/resume. The run was rejected only at the temporary-state cleanup check. The forensic mask was `0x00006000`, identifying the two radio-spare full-value comparisons. Gain-table state restored exactly (`0x1a41` saved/observed on both cores), `deaf_count` returned from 0 to 0, and no other cleanup bit fired.

The raw radio-spare reads were:

```text
saved:    core0=0x0072 core1=0x0072
observed: core0=0x00e4 core1=0x00e4
```

The reconstructed calculation's pre-rollback RX-IQ tuple was `(0,0,0,0)`. The automatic failed-run rollback then independently suspended/resumed the MAC and read-verified restoration of the original `(0,0,0,0)` tuple.

## Correct stock D6/E2 cleanup semantics

Instruction-level review of the preserved RV220W Broadcom `wl.ko` 5.60.120.9 rev3–6 `wlc_phy_cal_rxiq_nphy` path shows D6/E2 are temporary two-bit selectors. Setup modifies bits `[1:0]`; cleanup performs the equivalent of:

```c
and_radio_reg(pi, 0xD6, 0xFFFC);
and_radio_reg(pi, 0xE2, 0xFFFC);
```

It does not save and restore the entire register contents and does not require complete readback equality. Therefore the v1.14.33 `0x72 -> 0xe4` comparison was an invalid cleanup invariant. v1.14.34 retains raw saved/observed values for evidence but considers cleanup valid when the observed low two bits are zero.

## Final coefficient ambiguity in v1.14.33

The `(0,0,0,0)` calculated tuple is real pre-rollback evidence, but it is ambiguous. b43's existing `CalcRxIqComp` helper takes a final 16384-sample IQ estimate and restores the old coefficients internally when power/divisor validation fails. Because the helper returns `void`, the caller cannot distinguish a mathematically computed zero correction from a rejected estimator that silently restored the old zero tuple.

v1.14.34 leaves the ordinary helper unchanged and adds a diagnostic-only clone with equivalent calculation math. It records:

- final I power, Q power and IQ cross-product per core;
- per-core calculation error code;
- a bitmask of cores whose new compensation tuple was actually written.

Error codes are:

```text
0 = calculation accepted
1 = insufficient final IQ power
2 = A-term divisor zero
3 = B-term divisor zero
4 = core/mask mismatch
```

The diagnostic also records all three preceding 1024-sample gain-selection estimates for each core: I power, Q power, IQ product, derived selection power and packed gain. This distinguishes a dead/incorrect loopback stimulus from a failure specific to the final compensation estimate.

## 2.4 GHz setup retained

The active gate remains CA 2.4 GHz channels 1–11 only. The reconstructed rev3–6 setup continues to use the stock RFSEQCA RXDIS/TXEN fields and now explicitly uses the 2.4 GHz RFCTL pair `0x110/0x114`. The 5 GHz `0x140/0x148` values are not part of this experiment.

## Safety boundary

Nothing in v1.14.34 makes a failed run permissive. Calibration is still explicit and dual acknowledged, forced-PIO only, and restricted to N-PHY rev4 / BCM2056 rev3. The MAC must suspend and resume around both the active run and rollback. Temporary-state cleanup must pass before coefficients can be considered active. Saved coefficients are always restored and read-verified at the end of a completed experiment. No scan, association, AP mode, frame injection, cache/chanspec save, SPROM/MTD/NOR write or automatic normal-b43 calibration is introduced.

## Hardware decision tree

- If one of the three 1024-sample gain estimates already has little/no energy, continue reconstructing loopback/RF/gain setup.
- If gain-pass estimates are healthy but the final 16384-sample estimator fails, focus on the playback-to-final-calculation transition and estimator state.
- If both cores report `calc_error=0`, `calc_applied_mask=3`, and new nonzero coefficients, the reconstructed compensation math is working; decoded channel-8 receive during the observation then tests causality.
- If both cores report healthy final estimator values and `calc_applied_mask=3` but the tuple remains zero, zero compensation was genuinely calculated and RX-IQ imbalance is unlikely to be the sole decode blocker.
- Any real RFCTL/AFE/RFSEQ/gain/deaf-count/low-two-bit cleanup failure or coefficient rollback failure remains a stop condition for that boot.
