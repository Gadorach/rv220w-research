# RV220W v1.14.61 — operational RX capture hotfix

## Hardware result being corrected

v1.14.60 completed the qualified retained calibration transaction successfully on CA channel 8: natural primary return 0, cleanup mask 0, retained IQ `(2,1,0,5)`, and RCCAL `140/138/138`. The subsequent passive-RX observation was not valid because the RAM image has no external `timeout` command. The helper therefore returned tcpdump rc 127 immediately and sampled RX counters with effectively no observation interval.

This is classified as a userspace capture-runner defect, not a receiver/RF failure.

## v1.14.61 change

The kernel b43 patch remains exactly byte-identical to v1.14.60. The target helper now implements the eight-second capture entirely with shell primitives:

1. start `tcpdump` in the background;
2. sleep one second and confirm the capture process remains alive;
3. sleep seven additional seconds;
4. send SIGINT so tcpdump flushes its summaries;
5. `wait` for tcpdump and record its return status;
6. measure RX packet growth and captured frame count;
7. only if passive RX succeeds, issue the existing read-only `verify:retained` operation.

Telemetry includes `rxiq_observation_capture_backend=tcpdump-background-sigint`, `rxiq_observation_window_seconds=8`, `rxiq_observation_capture_started`, PID, signal rc and tcpdump rc.

## Qualification rule

A v1.14.61 PASS requires a healthy capture backend, RX packet growth, at least one captured monitor frame, zero association/stations, and the existing post-RX IQ/RCCAL/MAC-serialization gates. If the backend is unhealthy, the analyzer reports capture-runner failure and does not interpret zero traffic as RF evidence.

Automatic startup calibration, scans/probe requests, association, AP operation, user-data TX, frame injection and persistence remain blocked.
