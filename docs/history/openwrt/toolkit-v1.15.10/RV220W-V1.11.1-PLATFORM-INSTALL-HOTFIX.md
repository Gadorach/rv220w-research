# RV220W v1.11.1 platform-install hotfix

## Failure corrected

The v1.11.0 `openwrt-rv220w-platform-v1.5.0.patch` concatenated the complete v1.4.0 platform patch with a second diff for `target/linux/octeon/image/Makefile`. The second diff expected the RV220W definitions at file line 1, while the canonical full v1.4.0 patch places them after `Device/generic`. `git apply --check` therefore rejected both:

- an existing canonical platform v1.4.0 source tree; and
- a freshly cloned OpenWrt v25.12.5 source tree.

The persistent build then dropped `CONFIG_TARGET_octeon_generic_DEVICE_cisco_rv220w_persistent=y` during `defconfig` because the v1.5.0 device profile had never been installed.

## Corrected installation policy

The v1.11.1 installer uses the known-good full v1.4.0 patch as the clean-source base. It then performs one idempotent semantic update to `target/linux/octeon/image/Makefile`:

1. locate the exact existing `RV220W_CMDLINE` and `RV220W_FLASH_STAGE_CMDLINE` definitions;
2. add the persistent and persistent-writer command lines immediately after them;
3. locate `TARGET_DEVICES += cisco_rv220w_flash_stage`;
4. add the two persistent device definitions immediately after that target;
5. refuse duplicate, partial, or conflicting definitions;
6. run the complete platform verifier before writing the v1.5.0 marker.

No source reset, rebase, or clean is performed. The operation changes only the platform files already managed by this toolkit.

## Recovery from the observed session

The failed `git apply --check` did not modify the newly cloned tree. After installing v1.11.1, run:

```fish
./rv220w.fish platform install
./rv220w.fish platform verify
./rv220w.fish build persistent
./rv220w.fish build persistent-writer
./rv220w.fish verify
```

If an interrupted detached build still owns the workspace flock, identify and terminate that specific build process before rebuilding. Removing the lock pathname alone does not release an active `flock`.
