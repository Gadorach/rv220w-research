# RV220W v1.13.2 standard sysupgrade root alignment

The v1.13.1 build proved that the board-specific filesystem recipe was selected,
but OpenWrt's standard `scripts/sysupgrade-tar.sh` still rounds the `root`
member to a 1024-byte boundary. The hardware-hosted build produced:

```text
staged SquashFS bytes_used: 4,192,012
sysupgrade root member:     4,192,256
zero alignment suffix:            244
```

The first 4,192,012 bytes match the staged SquashFS exactly and the suffix is
all zero. This is standard tar-generation behavior, not Octeon's former
`pad-extra 128k` recipe.

Toolkit v1.13.2 therefore treats the raw SquashFS and archive member as two
related but distinct lengths. The host verifier decodes the little-endian
SquashFS v4 `bytes_used` field at superblock offset 40 and requires:

- `bytes_used` equals the staged SquashFS file length;
- the archive prefix through `bytes_used` is byte-identical to the staged file;
- the archive member is 1024-byte aligned;
- the suffix is fewer than 1024 bytes and entirely zero.

The RV220W stage2 runtime repeats the same structural checks on target. Because
the CN5010 is big-endian, it decodes the eight little-endian `bytes_used` bytes
explicitly. It writes only the first `bytes_used` bytes to the erased 25.375 MiB
rootfs partition, then verifies that exact trimmed file. The tar alignment bytes
are never written into the future automatic JFFS2 region.

Kernel-last ordering, metadata requirements, MTD geometry checks, configuration
preservation, readback verification and protection of `boot-chain` and
`uboot-env` are unchanged.
