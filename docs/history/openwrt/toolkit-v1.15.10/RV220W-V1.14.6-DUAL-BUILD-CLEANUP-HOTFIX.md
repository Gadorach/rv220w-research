# RV220W v1.14.6 dual-build cleanup/source-DTS recovery hotfix

## Trigger

The v1.14.5 updater stopped during its post-copy platform install with:

```text
error: DTS model is not the canonical Cisco RV220W platform model
[rv220w:error] RV220W platform install failed
```

The failure was valid. The OpenWrt target source DTS was no longer the canonical platform DTS.

## Root cause

`build_dsa_dual()` had defined `cleanup_dsa_dual_source()` but never registered that routine with an EXIT/INT/TERM trap. The function temporarily replaces `cn5010_cisco_rv220w.dts` with the selected full-RJ45/validation/WLAN profile and, for `wifi-discovery`, temporarily installs `994-rv220w-octeon-pci-irq-callback-lifetime.patch`. Without the trap, a successful build could leave both temporary source states behind.

The preceding v1.14.4 WLAN build therefore left the generated full-RJ45 DTS in the OpenWrt source tree. The next platform install correctly rejected its descriptive model string instead of silently treating it as the canonical platform source.

A related copy/paste error had also placed WLAN IRQ-staging code in `build_dsa_lan()`, where its variables are undefined under `set -u`. That path was not involved in the reported WLAN failure but is corrected here.

## v1.14.6 correction

- `build_dsa_dual()` now arms `trap cleanup_dsa_dual_source EXIT INT TERM` after all read-only prechecks and before the first temporary kernel-patch or DTS mutation.
- Cleanup restores the exact pre-build DTS by SHA-256 and removes only an exact copy of the temporary WLAN IRQ patch.
- `build_dsa_lan()` no longer contains the stray WLAN staging block.
- `platform install` now runs the existing conservative source-DTS recovery helper before platform verification.
- The recovery helper accepts canonical/local-format-compatible platform DTS files unchanged, restores recognized toolkit-generated LAN, dual-conduit, full-RJ45 and WLAN DTS states, and still refuses unknown local DTS content.
- `platform verify` remains read-only; it does not repair source state.

## Safety boundary

This hotfix does not change platform v1.7.5, the production DTS template, DSA patches, persistent image configuration, NOR partitioning, sysupgrade code, boot-chain policy, or the v1.14.5 BCM4322 fallback-SPROM content. RF remains blocked while the generic fallback SPROM policy reports `rf_qualified=0`.

The failed v1.14.5 updater copied toolkit v1.14.5 into place before stopping, so v1.14.6 is intentionally distributed as a direct v1.14.5 -> v1.14.6 repair updater.
