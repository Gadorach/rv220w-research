# RV220W v1.14.69 BCM4322 PCI INT0 routing correction

## Evidence boundary

The v1.14.68 `wifi-discovery` build succeeded and RAM-booted with the read-only `octeon-pci-irq-diag` module. The retained-calibration passive RX run reproduced the prior device-side state (`GEN_IRQ_REASON=0x00008100`, `DMA0_REASON=0x00010000`) while Linux IRQ110/CIU37 remained at count zero. The decisive new data were:

- BCM4322 PCI endpoint `0000:00:03.0`, vendor/device `14e4:432b`;
- PCI Interrupt Pin = 1 (INTA#), legacy INTx enabled;
- Linux b43 IRQ = 110, CIU bit 37 = PCI INT1;
- CIU `pci_int_pending=0x1`: physical PCI INT0/CIU36 asserted;
- CIU `pci_int_enabled=0x2`: only PCI INT1/CIU37 enabled.

This is a direct board-level routing mismatch, not a b43 DMA/PIO/calibration failure.

## Correction

`openwrt/wifi/993-rv220w-octeon-pci-int0-routing.patch` changes only the conventional-PCI map callback and only when all of these are true:

- device tree machine compatible is `cisco,rv220w`;
- PCI vendor/device is `14e4:432b`;
- root-bus slot is 3;
- interrupt pin is INTA# (`pin == 1`).

For that exact endpoint the callback returns `OCTEON_IRQ_PCI_INT0`. Every other device falls through to the upstream board-string/generic swizzle code unchanged.

The existing v1.14.4 callback-lifetime correction remains a separate `994-...` patch and still removes `__init` from the callback because the function pointer persists after init.

## Expected next hardware behavior

On this Linux/Octeon IRQ numbering, the prior INT1 assignment was IRQ110, so the corrected INT0 assignment is expected to appear as IRQ109/CIU36. More important than the Linux number is the direct CIU relationship: the b43 line should be CIU36 and `pci_int_enabled` should contain bit0.

Once request_irq unmasks INT0, one of three things should happen:

1. **Receiver recovers:** host IRQ count, b43 IRQ/DMA0/PIO counters and tcpdump/netdev RX advance. This qualifies the routing fix and moves work to ordinary RX quality/association validation.
2. **INT0 is enabled/pending but Linux still sees zero host IRQs:** investigate CIU edge/level delivery/ack behavior rather than SSB or calibration.
3. **Host/b43 IRQs advance but RX stops later:** use the existing DMA0 -> PIO -> frame/data/header -> b43_rx -> mac80211 counters to localize the next defect.

## Safety boundary

The release remains RAM-only for WLAN qualification. It adds no scan, probe request, association, AP mode, frame injection, user-data TX, NVM write, NOR write, persistent platform change, or automatic startup calibration. The CIU diagnostic remains read-only.
