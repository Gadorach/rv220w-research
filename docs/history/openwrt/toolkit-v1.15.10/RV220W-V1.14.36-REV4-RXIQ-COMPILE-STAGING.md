# RV220W v1.14.36 — genuine rev4 RX-IQ compile staging

## Release role

v1.14.36 is a **compile/integration checkpoint**, not an RF-active calibration release. It derives from the hardware-qualified/fail-closed v1.14.35 toolkit and leaves the public RX-IQ `run` gate blocked with `-EOPNOTSUPP` before rollback capture, MAC suspension, PHY/radio mutation, sample playback or coefficient changes.

The purpose of this release is to compile the reconstructed genuine rev4 helper primitives against the user's exact OpenWrt/backports source tree and expose any API, macro, patch-placement or compiler mismatch before a transaction runner is allowed to call them.

## Compile-staged primitives

The b43 `phy_n.c` patch now contains target-scoped helpers for the RV220W hardware tuple:

- N-PHY revision 4
- BCM2056 radio version `0x2056`, radio revision 3
- 2.4 GHz path
- two RX/TX cores

The staged groups are:

1. rev4 PHY loopback setup / exact restore / readback verification;
2. BCM2056 rev3 radio loopback setup / exact restore / readback verification;
3. transaction-wide TX-power-state capture plus calibration TPC-off entry;
4. lazy per-core forced-index base capture and signed index apply/release;
5. pre-rev7 2.4-GHz RX calibration gain search;
6. pre-rev7 RCCAL sweep with diagnostic-strengthened local rollback.

All top-level staging helpers are marked `__maybe_unused` because they are deliberately unreachable in this release.

## Signed TX-power-index correction

Broadcom's gain-table field is signed 8-bit. The row-0 2.4-GHz literal `128` therefore represents `-128`, a release sentinel. v1.14.36 encodes it explicitly as `(s8)0x80`. Numeric forced indexes lazily capture the per-core force base; any negative index releases that force state. The special `-1` gmval behavior belongs to the 5-GHz path and remains unsupported by this 2.4-GHz-only staging helper.

The standalone diagnostic transaction also snapshots both 84-entry adjusted-power table regions because toggling b43 TX power control reconstructs those tables. Final restore writes the exact saved images and verifies them rather than assuming a logical mode transition recreates byte-identical hardware state.

## RCCAL safety difference from stock

The stock RCCAL sweep leaves its selected RX `RXLPF_RCCAL_LPC` value installed and returns an encoded candidate. The v1.14.36 diagnostic helper deliberately restores the saved RX-LPC value before returning and exposes the candidate separately. A future outer transaction must explicitly commit any RCCAL result under a larger rollback snapshot. This keeps the sweep itself observational and readback-verifiable.

## Safety boundary

For v1.14.36 all of the following remain mandatory:

- host `collect-wifi --rxiq-calibration` fails before SSH;
- target `rv220w-wifi-probe rxiq-calibration` exits before interface/tune/debugfs mutation;
- kernel debugfs `run` returns `-EOPNOTSUPP` before any calibration mutation;
- the normal b43 rev3+ production calibration path is not replaced;
- no calibration cache/chanspec/NVM/NOR commit is introduced;
- hardware-qualified persistent platform v1.7.5 files remain byte-identical.

## Qualification for this release

The useful test is a normal `wifi-discovery` cross-build. A successful build qualifies patch/API integration only. There is **no useful RF-active v1.14.36 test**. Do not invoke `collect-wifi --rxiq-calibration` for this release; it is intentionally rejected.

The next release should build a transaction runner around these compile-qualified helpers, add fault-injection/rollback tests, and only then consider reopening the RF-active gate.
