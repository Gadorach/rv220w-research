# RV220W v1.14.7 — BCM4322 evidence integrity and physical-SPROM audit

## Hardware result promoted by this release

The v1.14.6 RAM-only `wifi-discovery` image crosses every discovery-only gate that previously blocked b43:

- cold-boot PCI enumeration identifies Broadcom `14e4:432b` at `0000:00:03.0`;
- the Octeon conventional-PCI IRQ-lifetime correction remains stable and assigns IRQ 110;
- the generic OpenWrt `brcm,ssb-sprom` provider registers and is requested for PCI `[0:3]`;
- SSB registers four cores;
- b43 binds the WLAN core at core revision 16;
- b43 identifies Analog 8, N-PHY type 4 revision 4;
- b43 identifies radio manufacturer `0x17f`, ID `0x2056`, revision 3;
- mac80211 creates `phy0` / a wiphy while UCI remains disabled.

This is **discovery qualification**, not RF qualification. Firmware initialization, scanning, association and transmission remain outside this gate.

## Why runtime PCI says 432c

OpenWrt's generic SSB fallback-SPROM implementation matches a provider by PCI bus/slot. If the fallback SPROM carries a nonzero product ID, it intentionally writes that ID into `bus->host_pci->device` before copying the decoded SPROM into SSB. The generic BCM4322 fallback therefore causes Linux runtime sysfs to report `14e4:432c` even though the real PCI enumeration at boot is `14e4:432b`.

v1.14.7 records these separately:

- `pci_boot_vendor` / `pci_boot_device`: physical enumeration evidence;
- runtime `vendor` / `device`: current kernel `pci_dev` state;
- analyzer flag `fallback_devid_override_observed` when the known `432b -> 432c` transition occurs with the generic fallback active.

The runtime override is no longer treated as disappearance of the BCM4322.

## Linux `ssb_sprom` is ASCII hex

The SSB sysfs ABI does not return raw SPROM bytes. Linux prints each 16-bit word as four uppercase hexadecimal characters and appends whitespace/NUL termination. The previous collector copied this text into a file named `.bin`; that name was misleading.

v1.14.7 instead preserves the target evidence as:

```text
rv220w-bcm4322-sprom-*.sysfs.hex
```

and the host-side `analyze-ssb-sprom.py` creates, separately:

```text
*.decoded.bin
*.decoded.bin.sha256
*.analysis.txt
*.analysis.json
```

No SPROM write path is used.

## First physical-shadow finding

The first v1.14.6 target capture is 882 bytes of sysfs text, containing 880 hexadecimal characters plus terminators. It decodes to exactly 440 bytes, i.e. the revision-4-and-later SSB SPROM size.

The decoded physical shadow has:

- revision 8;
- subsystem vendor `0x14e4`;
- PCI product field `0xffff`;
- board revision word `0x1302`;
- TX/RX chain masks `3/3`;
- a plausible 2.4 GHz FEM word and non-erased power-data words for cores 0 and 1;
- many erased `0xffff` fields and an invalid/incomplete MAC field;
- stored CRC `0x5a`, but calculated SSB CRC `0x34`.

That explains why normal SSB SPROM validation falls through to the platform fallback. The physical shadow is valuable reconstruction evidence, but its failed CRC and partially erased fields mean it must **not** be promoted directly into RF calibration.

## b43 capabilities debugfs state

The custom `capabilities` file is created for `phy0`, but b43's common debugfs read wrapper refuses reads until the device reaches `B43_STAT_INITIALIZED`. The discovery image intentionally leaves the UCI radio disabled and does not start firmware, so a present file that returns the pre-init error is expected.

v1.14.7 reports that state as `DEFERRED`, not `FAIL`. Firmware is likewise reported as `inventory-present-not-loaded` unless there is actual load evidence.

## RF boundary

The following remain prohibited by this gate:

- `passive-scan`;
- DMA/PIO reload intended to start the radio;
- association or AP operation;
- 5 GHz/DFS testing;
- persistent WLAN enablement;
- SPROM writes;
- using the invalid physical shadow as calibration;
- claiming HT/AMPDU/40 MHz parity.

The next engineering task is calibration provenance/reconstruction: search preserved stock images and other board evidence for RV220W-specific Broadcom variables, compare those against the physical shadow and generic fallback, then construct only a well-supported board-specific fixup set before any RF activation.

## Production-core status

No hardware-qualified persistent/platform file changes in v1.14.7. Platform integration remains v1.7.5; boot-chain, DSA, NOR layout, persistent SquashFS/JFFS2 and CLI/LuCI sysupgrade behavior are unchanged.
