# RV220W v1.14.16 — race-free b43 SSB rebind MAC gate

## Hardware result that triggered this hotfix

The v1.14.15 image built and RAM-booted normally. Native physical SPROM consumption remained qualified and b43 created a new wiphy after `apply-stock-mac`, but the helper reported the expected stock WLAN identity (`a4:93:4c:b1:42:aa`) while `/sys/module/b43/parameters/macaddr` was empty. The subsequent receiver-init command correctly refused because the stock identity gate had not passed.

The old helper unloaded `b43` and then invoked `modprobe b43 macaddr=...`. The SSB WLAN device remains present across the module unload, so reloading by module arguments is vulnerable to an automatic rebind/reload occurring before the explicit command takes effect.

## v1.14.16 approach

The custom `macaddr` parameter is changed from read-only `0444` to root-writable `0644`. `apply-stock-mac` no longer unloads b43. It:

1. keeps every UCI radio disabled;
2. identifies the SSB device currently bound to the `b43` SSB driver;
3. saves the current `pio` and `macaddr` values;
4. unbinds that SSB device from b43;
5. writes and verifies the requested RAM-only parameter values;
6. binds the same SSB device back to b43;
7. verifies that the core rebound and records `b43_ssb_rebind=PASS`.

Because b43 device registration is repeated on bind, the existing `b43_wireless_init()` override consumes the requested MAC when the wiphy is recreated. No wireless interface is raised by this operation.

If any step after unbind fails, the shell trap restores the previous parameter values and attempts to rebind the same SSB core before exiting.

## RF boundary

This is still an identity-only gate. `apply-stock-mac` does not request firmware start, receiver start, scan, association, AP mode, supplicant/hostapd, SPROM write, OTP operation, or NOR write. The existing `receiver-init --country CC --ack-rf` remains a separate explicit step, and passive scan remains blocked until receiver-init is hardware-qualified.
