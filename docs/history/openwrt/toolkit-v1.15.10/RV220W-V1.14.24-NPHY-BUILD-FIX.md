# RV220W v1.14.24 — N-PHY diagnostic build correction and artifact provenance

## What the v1.14.23 hardware run actually proved

The v1.14.23 N-PHY/IQ diagnostic did not reach hardware. The OpenWrt parallel build failed in `package/kernel/mac80211`, then the automatic serial `-j1 V=s` retry failed at the same patch. The actual backports preparation log showed:

- all four new `main.c` hunks applied;
- the first `debugfs.c` hunk, whose only purpose was to add three headers near the top of the file, failed;
- the `debugfs.h` hunk applied;
- all three later substantive `debugfs.c` hunks applied;
- OpenWrt then aborted mac80211 preparation.

No current ELF could therefore have been produced. The TFTP helper subsequently found the already-existing v1.14.22 `wifi-discovery` ELF and booted it. That older image has no `nphy_rxdiag` debugfs node, which is why the collector produced `band=unknown`, no frequency or IQ samples, and `finding=invalid-capture`. Those values are **absence of the new instrumentation**, not measurements of the RF path.

## Patch correction

The v1.14.23 patch used a separate source-header hunk for:

```c
#include <linux/delay.h>
#include "phy_n.h"
#include "radio_2056.h"
```

That hunk was brittle against OpenWrt's backports source layout. v1.14.24 removes it and places the same three file-scope includes at the start of the already-proven `debugfs.c` insertion hunk immediately following `mmio32write__write_file()`. C preprocessing permits file-scope includes there, and every new diagnostic reference occurs after that point. No N-PHY/IQ algorithm or register operation is changed.

## Fail-closed artifact handling

Before a `wifi-discovery` world build begins, the build helper now removes the previously staged:

- `.elf`;
- `.elf.sha256`;
- `.readelf.txt`;
- `.build-info`.

If the parallel build fails and the serial fallback also fails, the build returns failure and there is no staged WLAN ELF. Only after a successful world build and ELF verification does `stage_initramfs` recreate the artifact and write `.build-info` containing the toolkit version, build mode, label, ELF SHA-256 and UTC staging time.

`tftp-boot --profile wifi` and `--profile wifi-discovery` now require that sidecar and refuse to boot unless its toolkit version equals the currently installed toolkit, its mode is `rv220w-wifi-discovery-initramfs`, and the current ELF SHA-256 equals the recorded SHA. This is intended to make a stale fallback boot impossible after any future WLAN build failure.

## RF policy

The intended v1.14.23 diagnostic remains unchanged in v1.14.24: forced PIO, native physical SPROM, MTD-derived stock MAC, fixed-channel receive state plus N-PHY hardware IQ estimator, and no scan/association/AP/injection/RF override/calibration sequence/user traffic. The test must be rerun on a newly built v1.14.24 image before drawing any conclusion about N-PHY or BCM2056 receive state.
