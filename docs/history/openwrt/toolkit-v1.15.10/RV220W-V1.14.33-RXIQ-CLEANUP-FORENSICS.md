# RV220W v1.14.33 — RX-IQ cleanup-forensics gate

## Hardware evidence from v1.14.32

The first real reconstructed RX-IQ run occurred on CA channel 8 / 2447 MHz. The monitor interface tuned successfully, the expected MTD-derived WLAN MAC and forced-PIO state were present, and the calibration control entered with verified b43 MAC suspend/resume.

The kernel routine returned `-EIO` (`last_rc=-5`) with `cleanup_complete=0` and `active=0`. The wrapper then executed its failed-run rollback path. Rollback returned success, verified a second MAC suspend/resume cycle, and read back the original live RX-IQ coefficient tuple `(0,0,0,0)` exactly. No calibration result was left active.

This means v1.14.32 failed at or before the temporary-state cleanup verification boundary; it did not fail the outer MAC-serialization or coefficient-rollback safety boundary.

## Why v1.14.33 does not weaken cleanup

The v1.14.32 PHY routine collapses all temporary-state restoration mismatches into one `restore_ok=false`, later promoted to `-EIO`. That is insufficient to distinguish:

- per-core RFCTL TX/RX restoration;
- per-core AFE override/core restoration;
- per-core RFSEQCA restoration;
- final RESET2RX completion;
- RFSEQ gain-table restoration;
- BCM2056 radio-spare restoration;
- `deaf_count` restoration.

v1.14.33 leaves the success condition unchanged. Any mismatch still sets cleanup failure, prevents `active=1`, returns failure, and causes immediate coefficient rollback.

## Cleanup failure mask

`cleanup_fail_mask` uses the following bits:

| Bit | Meaning |
|---:|---|
| 0 | core0 RFCTL TX readback mismatch |
| 1 | core0 RFCTL RX readback mismatch |
| 2 | core0 AFECTL_OVER readback mismatch |
| 3 | core0 AFECTL core readback mismatch |
| 4 | core0 RFSEQCA readback mismatch |
| 5 | core1 RFCTL TX readback mismatch |
| 6 | core1 RFCTL RX readback mismatch |
| 7 | core1 AFECTL_OVER readback mismatch |
| 8 | core1 AFECTL core readback mismatch |
| 9 | core1 RFSEQCA readback mismatch |
| 10 | final RESET2RX sequence still busy/timed out |
| 11 | RFSEQ gain-table core0 mismatch |
| 12 | RFSEQ gain-table core1 mismatch |
| 13 | radio spare core0 mismatch |
| 14 | radio spare core1 mismatch |
| 15 | N-PHY `deaf_count` mismatch |

The diagnostic also records saved/observed values for the final gain-table entries, both radio-spare registers and `deaf_count`.

`primary_rc` records the operation result before a cleanup-only mismatch is promoted to `-EIO`. `failure_stage` is:

- `0`: no direct operation failure;
- `1`: core0 RESET2RX timeout;
- `2`: core0 tone/sample operation failure;
- `3`: core1 RESET2RX timeout;
- `4`: core1 tone/sample operation failure;
- `5`: cleanup-only failure promoted to `-EIO`.

## Calculated coefficient evidence before rollback

v1.14.32 restored the saved coefficients before reading the diagnostic `after` tuple when the run failed. That made a safe failure indistinguishable from a calibration that calculated zeros.

v1.14.33 instead reads the live calculated tuple into `after_*` immediately after the reconstructed routine finishes, then performs the same fail-closed restoration of `before` if the run failed. This does not leave the calculated tuple active; it only preserves what was calculated as evidence.

## Qualification rule

A cleanup mismatch remains a failed active experiment. The host analyzer may classify it as `rxiq-calibration-cleanup-mismatch-rollback-safe` only when:

- channel, MTD identity and PIO gates pass;
- run MAC suspend/resume pass;
- cleanup forensic fields are present;
- failed-run rollback MAC suspend/resume pass;
- rollback verification and exact coefficient match pass;
- no kernel b43/RF-sequence error indication is present.

The analyzer still returns non-zero for this finding. It is a useful forensic failure, not a successful calibration.
