# RV220W v1.14.4 Octeon PCI IRQ callback lifetime correction

## Hardware result that triggered this change

The v1.14.3 `wifi-discovery` image passed the prior mac80211 patch-order build gate and TFTP-loaded successfully. Linux enumerated the RV220W WLAN endpoint as conventional PCI `14e4:432b` and assigned its BAR. During `/etc/modules-boot.d` processing, loading `ssb` caused an immediate kernel fault while the PCI core was assigning the device IRQ.

The captured call chain is:

```text
ssb init_module
  -> driver_register / PCI probe
  -> pci_device_probe
  -> pci_assign_irq
  -> pcibios_map_irq
  -> stale Octeon IRQ mapping callback
```

The exception PC was `0xffffffff81d19004`, inside the image's `.init.text` range (`0xffffffff81ceb000` through `0xffffffff81d197c7`). The bytes at the fault site had already been overwritten with initramfs shell-script text, confirming that the callback target had been reclaimed rather than identifying an SSB register-access failure.

The automatic reboot then returned to the previously installed persistent image. The subsequently collected `initial-b43-probe` snapshot therefore reported `profile=persistent`, no loaded `ssb`/`b43`, and no b43 firmware directory; those observations do not describe the crashed WLAN RAM image.

## Linux 6.12.94 lifetime bug

`arch/mips/pci/pci-octeon.c` has a persistent global function pointer:

```c
int (*octeon_pcibios_map_irq)(const struct pci_dev *dev, u8 slot, u8 pin);
```

`pcibios_map_irq()` dispatches through that pointer whenever a PCI driver needs an IRQ mapping. The conventional-PCI setup path stores `octeon_pci_pcibios_map_irq` into it, but Linux 6.12.94 declares that callback `__init`. Once init memory is freed, a deferred PCI driver probe can therefore call reclaimed memory.

The Octeon PCIe equivalent callback is not marked `__init`, which is the correct lifetime for a function retained behind the same persistent pointer.

v1.14.4 carries this one-line correction:

```diff
-int __init octeon_pci_pcibios_map_irq(...)
+int octeon_pci_pcibios_map_irq(...)
```

## Isolation from the qualified persistent core

This correction is intentionally **not** installed by `platform install` and is not added to the normal target patch stack. `build wifi-discovery` temporarily stages it as:

```text
target/linux/octeon/patches-6.12/994-rv220w-octeon-pci-irq-callback-lifetime.patch
```

The build trap removes that exact patch and cleans `target/linux` before returning. A differing file at that path is refused rather than overwritten or deleted.

Accordingly, the hardware-qualified platform v1.7.5 persistent configuration, DSA patches 995-999, persistent image generator, NOR layout, and sysupgrade implementation remain byte-identical to the qualified v1.13.7 core.

## Evidence-integrity correction

`collect-wifi` now reads `/etc/rv220w-build-profile` first and refuses the target unless it reports exactly `profile=wifi-discovery`. The target snapshot script performs the same check. This prevents a kernel panic followed by an automatic persistent reboot from being analyzed as though it were the WLAN discovery image.

The analyzer also records a `wifi_discovery_profile` gate and reports the source profile explicitly.

## Next qualification gate

Rebuild and TFTP-boot `wifi-discovery`. Before any RF scan, confirm:

1. no IRQ-assignment panic;
2. SSB devices enumerate;
3. `ssb` and `b43` remain loaded;
4. b43 firmware inventory/load state is visible;
5. SPROM is readable if exposed by sysfs;
6. a wiphy appears;
7. the b43 capabilities report exposes core/PHY/transfer/MAC identity;
8. the permanent MAC can be compared with the stock `platform base + 4` policy.

Only after those gates are reviewed should `reload-dma`, `reload-pio`, a RAM-only MAC override, or the explicitly acknowledged 2.4 GHz passive scan be used.
