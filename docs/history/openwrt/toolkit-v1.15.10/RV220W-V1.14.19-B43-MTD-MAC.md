# RV220W v1.14.19 — generic b43 MTD-derived permanent MAC

## Why U-Boot environment persistence is not used

The v1.14.18 hardware trace shows U-Boot successfully reads the protected base MAC and derives the stock WLAN MAC, but Linux's effective command line omits the custom WLAN MAC/PIO tokens even when `bootoctlinux` is invoked with `endbootargs`. Persisting variables with `saveenv` would add a flash mutation without changing the kernel's demonstrated command-line source.

## First-probe identity source

The wifi-discovery image instead ships static source metadata in `/etc/modules.conf`:

```text
options b43 pio=0 macaddr_mtd=boot-chain macaddr_mtd_offset=0x6ff00 macaddr_increment=4
```

The b43 implementation is generic. Explicit `macaddr=` has first priority. Otherwise, when `macaddr_mtd=` is non-empty, b43 opens that named MTD partition, reads `ETH_ALEN` bytes at `macaddr_mtd_offset`, validates the base unicast address, applies `macaddr_increment` as a checked big-endian 48-bit addition, validates the derived address, and calls `SET_IEEE80211_PERM_ADDR()` before normal registration. The MTD handle is released immediately after the read.

The patch has no MTD write or erase path and contains no RV220W partition, offset, increment or MAC constant. The board-specific profile supplies those values. On the qualification unit the independent expected calculation remains `a4:93:4c:b1:42:a6 + 4 = a4:93:4c:b1:42:aa`.

## Qualification sequence

1. Build and RAM-boot `wifi-discovery` normally; no extra U-Boot MAC transport is required.
2. Run `collect-wifi --apply-stock-mac stock-mac-qualification`. This is a verifier only.
3. Require MTD source `boot-chain`, offset `458496`, increment `4`, PIO `0`, the expected b43 first-probe log, and an unraised temporary managed interface inheriting the expected MAC.
4. Only after identity verification passes, run the explicit `receiver-init --country CA --ack-rf` gate on the same boot.
5. Passive scan/association/AP remain blocked until receiver-init evidence is reviewed.
