# RV220W v1.14.94 — persistent-WiFi boot-check global daemon correction

## Hardware result

v1.14.93 successfully wrote and read back the candidate rootfs, then TFTP-booted the manifest-qualified non-initramfs candidate kernel against the NOR rootfs. The boot reached the final radio-safety portion of `boot-check`.

The checker had already accepted the candidate build profile, protected partition geometry, `/rom` SquashFS, `/overlay` JFFS2, exact NOR SquashFS prefix, b43/SSB, `pio=0`, BCM4322 MTD-derived MAC, IRQ109, at least one `wifi-device`, zero `wifi-iface` sections and `disabled=1` for every radio. It then failed only because `pidof wpa_supplicant` was non-empty.

## Why that is a validator bug

The toolkit had already encountered and qualified this OpenWrt behavior in v1.14.83: installing the supplicant package can leave an interface-less global wpa/hostapd control daemon running even when no wireless interface exists and all radios are down. A PID alone does not prove that the radio is active.

## Correct invariant

v1.14.94 preserves every UCI disabled-radio gate and additionally requires `iw dev` to report **zero wireless netdevs**. Global `wpa_supplicant` and `hostapd` PIDs are recorded as telemetry and permitted only in that no-netdev state. Any wireless interface while the candidate is supposed to be inert remains a hard failure.

This is a host-side streamed validator change only. Candidate rootfs/kernel artifacts and the entire OpenWrt build tree are unchanged. Kernel NOR write remains blocked.
